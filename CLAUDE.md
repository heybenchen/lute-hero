# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Lute Hero is a multiplayer tabletop board game where Bards defeat monsters using music. Players navigate a 16-space grid board, encounter monsters spawned by genre tags, use songs with slotted dice to deal damage (with genre-based multipliers), earn Fame and EXP, and finish with a 3-verse Final Showdown against The Eternal Silence. It plays two ways: **hotseat** (everyone on one device) and **online multiplayer** (lobbies with join codes, server-authoritative state on Vercel).

## Tech Stack

React 18 + TypeScript (strict) + Vite + Zustand + Tailwind CSS. Server: Vercel Node functions in `api/` + Upstash Redis. Tests use Vitest (jsdom for UI, node for `api/__tests__`). Path alias `@/` maps to `src/` — but **shared code (`src/types`, `src/engine`, `src/game-logic`, `src/data`, `src/net/protocol.ts`) must use relative imports** because the serverless functions import it directly.

## Architecture

**The engine** (`src/engine/`) is the single source of game rules: a pure, deterministic reducer `applyAction(state, action, ctx)` over a serializable `EngineState`. Every mutation is one atomic `GameAction` (START_GAME, MOVE, PLAY_SONG, END_COMBAT, END_TURN, BUY_DIE, PLAY_SHOWDOWN_SONG, …), validated by `validate.ts` (rule legality + online seat authorization). `ctx` injects a seeded RNG (`mulberry32`) and id factory so the server and hotseat produce identical mechanics; all randomness in `src/game-logic/` and `src/data/` takes an `rng` parameter (defaulting to `Math.random`). `applyAction` returns `EngineEvent`s (dice rolls, damage, showdown beats) that drive UI animations.

**Drivers** (`src/drivers/`) own the authoritative state per play mode and push it into the store:
- `LocalDriver` — hotseat: applies actions synchronously, persists saves to localStorage (v9)
- `RemoteDriver` — online: POSTs actions to the API, mirrors state from the SSE stream, dedupes animation events per action seq (actor animates from the POST response, spectators from SSE)

**The store** (`src/store/index.ts`) is a render mirror: engine state (combat flattened to top level) + UI state (mode, connection, lobby) + one `dispatch(action)` routed to the active driver. Selectors: `selectCurrentPlayer`, `selectCanAct` (turn gating), `selectCanPerform` (showdown gating), `selectIsHost`.

**The server** (`api/`) is Vercel Node functions sharing the engine via relative imports: `lobbies/` (create, join-by-code; the same token rejoining gets its seat back — that's reconnect), `games/[id]/actions` (validated engine actions, crypto-seeded RNG, idempotent clientActionIds, CAS retry), `games/[id]/stream` (SSE: snapshot on connect, per-action updates, presence deltas, `goodbye` before the duration cap). Storage is Upstash Redis behind `api/_lib/redis.ts` (`RedisLike` with atomic Lua CAS; in-memory fallback for tests/dev). `scripts/api-dev.ts` runs the same handlers locally.

**Identity** (`src/net/identity.ts`): anonymous `crypto.randomUUID()` token per browser in localStorage; sha256 hash binds it to a seat. `lute-hero-online-session` stores the current game for auto-rejoin on reload.

**Components** in `src/components/game/` map to game systems: `Board/` (4x4 tile grid), `Combat/` (battle modal with spectator mode), `PlayerPanel/` (turn actions + presence dots + host skip-turn), `DraftShop/` (Studio purchases), `Showdown/` (final boss), `FinalSummary/`, `DebugPanel/` (playtest console). `src/components/lobby/` holds `ModeSelect` and `LobbyRoom`. Fights (`Combat/`) and the Final Showdown share their song UI: `Combat/SongCard` and `SongGrid`, the reroll button that sits on the most recently rolled dice (`RerollPill` + `makeReroll`: free with Bebop, else 1 Inspiration), the immunity icon (`songIsImmune` in `damageCalculator.ts` decides it for a monster or the boss, counting Crossover), and the performer's genre panel (`CombatStyles`). The concert screen also holds the per-play choices (Gospel's "call it", Soul's paid bonus) and the refresh button on a spent song (Gospel after a called win, Blues for Inspiration). Keep new shared song behaviour there rather than in either screen. All write through `dispatch`; never mutate state directly.

**3D dice** (`src/components/dice3d/`) are a UI-only layer over rolls the engine has already decided. The store announces every `diceRolled` event (own dispatches and spectators' SSE entries) to `diceBus`, which queues throws for `DiceRollHost` (always mounted in `App`, lazy-loads the three.js/cannon-es `DiceRollOverlay` chunk). `simulate.ts` runs a cannon-es throw and `dieShapes.labelsShowing` relabels faces so the landed face shows the real value. `useRollAnimation(..., dieId)` keeps cards tumbling while their die is in flight; await `diceBus.whenSettled()` before showing result popups. No host mounted, reduced motion or no WebGL means a no-op.

**The Bestiary** (`/bestiary`) is a standalone Monster Manual on the same deployment, independent of the game engine. `main.tsx` does path routing (`/bestiary` → `src/bestiary/Bestiary.tsx`, everything else → the game `App`), each side lazy-loaded so their bundles stay separate. Shared roster/effects/level-builder live in `src/bestiary/data.ts` and feed both the UI and the CRUD API (`api/monsters/index.ts` for GET/POST, `api/monsters/[id].ts` for PUT/DELETE), which persists to the same Upstash Redis via `getRedis()` under `bestiary:monsters` (seeded on first read, in-memory fallback in dev/tests). `vercel.json` adds a SPA rewrite (excluding `/api`) so the route deep-links in production.

**The Songbook** (`/songbook`) is a standalone reference for every Studio genre, routed in `main.tsx` like the Bestiary and lazy-loaded (`src/songbook/Songbook.tsx`). Rules, prices, flavour and setting values are read live from `src/data/styles.ts` and the default tunables, so they follow the game; only the simulated win rates, each genre's group and trigger, and its previous price are stored in `src/songbook/data.ts` (with a KEEP IN SYNC note pointing at `songStyles.md`). A test checks that every genre has an entry.

**The Rulebook** (`rulebook/RULEBOOK.md`, with diagrams in `rulebook/img/`) is the game's rules written as a printable board-game rulebook. The diagrams are generated by `npx tsx scripts/rulebook-visuals.ts`, which also refreshes the genre list in Appendix A from the live rules and reads numbers (monster HP/Fame/EXP, dice prices) from the tunables. `src/rulebook.test.ts` checks the book's numbers and genre list against the game, so a balance change fails it until the book is updated: edit the prose, then run the script. The print-ready `rulebook/RULEBOOK.pdf` is a rendering of the book, so regenerate it after edits (markdown to HTML, then Chromium print to Letter). When a rule changes (turn structure, fights, the Studio, the Showdown), update the matching rulebook section too.

**Types** are centralized in `src/types/index.ts`; wire types (GameDoc, Snapshot, SSE messages, debug presets) in `src/net/protocol.ts`.

**Tunables** (`src/data/tunables.ts`) hold every balance number. They live in `EngineState.tunables`, so tweaks persist in saves and sync to every online seat, and `applyAction` publishes them to a module-level active set via `withTunables` for the duration of one reduce — that is why game-logic reads `getTunables().x` instead of taking a parameter. Never re-add a hardcoded balance constant: add a field plus a `TUNABLE_FIELDS` entry instead.

## Key Game Mechanics

- **Player-facing words**: everything players read calls a fight a **concert**; a monster is **moved** (wounded) or **won over** (tamed/defeated) and becomes a fan; HP is **Resolve**; a reroll is an **encore**; a featured song is a **guest song**; retreating is **ending the concert**. Code identifiers (`combat`, `PLAY_SONG`, `currentHP`, `REROLL_SONG`, `featuredPlayerIds`, …) keep their old names so saves and online games stay compatible. `src/rulebook.test.ts` keeps fighting words out of the rulebook.

- **Damage flow**: Roll dice (crits cascade) → genre multipliers (2x vulnerable, 0x immune) → damage hits ONE chosen target monster (songs are single-target, not AOE)
- **Combat rewards**: Fame per kill; EXP only for monsters the bard *wounded* (`currentHP < maxHP`) — every monster on a victory, but untouched ones pay nothing on a retreat (`computeCombatRewards`). Retreat is allowed at any point. On a retreat, won-over monsters' chips leave the board and every monster that was wounded but not defeated gains one chip of its element (levels up, capped); untouched monsters are left as they were. The tunable `retreatLevelsUpAll` (default 0) switches back to levelling up every monster left; `npx tsx scripts/retreat-rule-sim.ts [games]` compares the two rules (game length, EXP, board size).
- **Song economy in combat**: defeating the target returns that song's dice (it stays playable); damaging without defeating spends the song for that fight (`combat.spentSongIds`). There is no fixed song cap.
- **Featured songs**: in a fight, the bard may play one song from each other bard on the same space (`combat.featuredPlayerIds`). Hotseat plays it directly (`PLAY_FEATURED_SONG`; players always agree); online the fighter asks (`REQUEST_FEATURE`, which pauses their plays) and the guest's seat answers (`ANSWER_FEATURE`; either side can decline/withdraw). Featured songs roll plain (no genres), never spend or refresh anything (and can't be called for Gospel), and can't be rerolled. A featured tame is a `KillCredit` with `featuredPlayerId`: the guest gets the rounded-down half of that monster's Fame and EXP (`computeCombatRewards().guestRewards`).
- **Chip limits**: a space holds any number of monster chips, but at most `maxTagsPerGenre` (default 5) of the *same* element — the cap that keeps a monster from exceeding Lv5. Use `canAddGenreTag`/`addGenreTag`/`capGenreTags` from `graphBuilder` rather than checking `genreTags.length`.
- **Monster spawning**: one monster per unique genre tag on a space; duplicate tags raise its level (a monster's level equals its genre's tag count, so the board chip matches the fight; capped at Lv5); fame per kill = 5/10/25/50/75 and EXP = 1/2/3/4/5 by level (Lv1–Lv5+)
- **Monster HP**: uniform per level, from `monsterBaseHp` (8) × the level multiplier — 8/14/24/40/60 for Lv1–5. Templates carry no HP: `MonsterTemplate.tier` only paces *which* monster shows up as rounds progress. Use `monsterSpawnHp(level)` rather than recomputing.
- **Turn structure**: Move up to 2 connected spaces (there is no Inspiration travel; the engine's `MOVE` is one step, and the board highlights every space within the moves left via `getReachableMoves` — clicking a far one dispatches one `MOVE` per step along its shortest path, and "Undo move" takes back one step), fight 1 combat, shop in the Studio, end turn. Clearing every monster on a space earns +1 Inspiration and radiates a chosen element to neighbors. Combat does NOT open the Studio — the Studio button pulses (`hasShoppedThisTurn`) until the player visits it.
- **Round end**: after every player has taken a turn the board is reinforced automatically — one chip of *every* element per bard (`roundEndChipsPerElement`, default 1), scattered to random spaces with `scatterChipsRandomly` so no two of that round's chips share a space. No player input; the round just advances. This is the only way the board grows.
- **Phase progression**: any single player reaching the fame gate (default 200, `tunables.fameFinalBossThreshold`) grants one "final turn," then triggers the Final Showdown (3 verses; each verse a bard performs one element — every die of it rolls together via `showdownElementSongs`, rerollable with Inspiration — between verses the boss becomes immune (0×) to the strongest performance's element — it has no weakness; damage = fandom; most total fans wins)
- **Genres** (called styles in code): Studio purchases that change how ALL of a bard's songs play — a bard holds at most `maxStyles` (2). Everything players read says **genre** (the Studio's Genres shelf, the Songbook, the rulebook); songs and dice belong to **elements**. Two are on the shelf (`EngineState.styleOffers`), redrawn at the start of every turn (`beginTurn`) or for Inspiration (`REFRESH_STYLE_OFFERS`); `BUY_STYLE` at the cap names one to replace. Catalog + live rule text in `src/data/styles.ts`. Players see real-world genre names; the ids stay fixed so saves keep their genres: `staccato` Gospel, `coda` New Age, `ostinato` Indie, `rubato` Bebop, `virtuoso` Bluegrass, `fortissimo` Opera, `fermata` Blues, `counterpoint` Crossover, `tutti` Barbershop, `overture` Screamo, `bravo` Disco, `ispirato` Pop, then the kebab-case ones `hometown-hero` Country, `studio-regular` Lo-fi, `inspired-play` Soul, `steady-hands` Baroque, `street-performer` Rap, `chain-reaction` House, `swarm-singer` Orchestra, `jam-session` Mariachi, the nine added with the rename (`punk`, `soft-rock`, `prog-rock`, `ska`, `k-pop`, `emo`, `trance`, `grunge`, `dubstep`), and `trip-hop` (once per turn, `MOVE { anywhere: true }` to any space, costing no regular move; `EngineState.tripHopUsed`, reset in `beginTurn`, refunded by `UNDO_MOVE`). The retired `small-ensemble` and `double-time` ids are dropped from saves by `normalizeEngineState`. The kebab-case genres are data-defined specs that `studioSpec()` (`src/data/styleSpecs.ts`) builds from the live tunables, and `specsOf(player)` includes them, so the engine and the smart bot handle them through the spec path (once-per-turn ones are tracked in `combat.specFired`; their notes come from `StyledRolls.specApplied`). Price keys follow `styleCostKey(id)`; roll/damage effects in `src/game-logic/styles/styleEffects.ts`, shared by combat and the showdown. "Once per turn" genres fire automatically and are tracked in `combat.stylesUsed` (part of the reroll snapshot, so rerolls replay them) — except the four the bard chooses: Bebop (`rubato`), a free `REROLL_SONG { rubato: true }` that keeps the higher of the two rolls; Blues (`fermata`), `LINGER_SONG` to refresh a spent d20 song for Inspiration; Gospel (`staccato`), a `PLAY_SONG { staccatoCall: true }` that spends the once-per-turn use and, if that song wins its monster over, arms `combat.rallyReady` so the bard refreshes any spent song (`staccatoMaxFaces` 20) with `RALLY_SONG`; and Soul (`inspired-play`), a `PLAY_SONG { inspiredPlay: true }` that pays Inspiration once to switch `combat.soulActive` on, putting its bonus on every song for the rest of the concert (encores keep it), allowed only when `EngineState.turnStartInspiration` (recorded in `beginTurn`) is high enough. An encore replays the last play's Gospel call (`combat.lastPlayFlags`). Pop (`ispirato`) pays its Inspiration in `START_COMBAT`, before every concert. Bluegrass (`virtuoso`) rolls every d4/d8 twice (always on, not once per turn). New Age (`coda`): replacing it while its 7th song holds a die needs `BUY_STYLE { giveUpSongId }`; that song's die is lost and the 7th song's die takes its slot. K-Pop pays in `endCombat` for 3 / 4+ wins in one concert (`kPopFame3`/`kPopFame4`). Trip-Hop is handled in the `MOVE` reducer, not as a spec. Grunge (`afterMove`) and Dubstep (`afterWin`; rolls twice and adds `dubstepBonus`, tunable `dubstepAdvantage`/`dubstepMultiplier`/`dubstepOncePerTurn`) read `combat.lastPlayResult` ('won' | 'moved' | 'missed'); Emo is a `PLAY_SONG { emoFinale: true }` that adds `emoBonus` and sets `combat.finaleDeclared`, after which no song can follow (encores keep the bonus); Opera raises the rolled value of d20s (a flat bonus when `fortissimoRaisesFace` is 0); Punk adds `critFlat` on a crit; Baroque raises a low face (`lowFaceBonus`/`lowFaceAtMost`, it can crit); Orchestra counts the monsters still standing and raises the rolled value (`critBonus`); House (`chain-reaction`) has no cap by default (`chainReactionCap` 0) and builds within a showdown verse at `chainReactionShowdownBonus`. In fights a song is performed by clicking its die. New Age (`coda`) adds a 7th song (`<playerId>-coda`); losing it returns that song's die as an unclaimed reward. Every price and effect size is a tunable in the Genres group. Rule-shaping limits are tunables too (`fermataMinFaces`/`fermataInspirationCost`, `staccatoMaxFaces`, `rubatoMaxFaces`/`rubatoUsesPerTurn`, `virtuosoMinFaces`/`virtuosoMaxFaces`, `tuttiElements`, `ispiratoMin`/`ispiratoPerTurn`, `ostinatoMaxFaces`/`ostinatoCascadeBonus`, `bravoMinLevel`, `inspiredPlayMin`/`inspiredPlayCost`, `progRockFrom`, `steadyHandsAtMost`/`steadyHandsBonus`) and `styleRule` writes the live rule text from them; `docs/style-lab-report.md` holds the older simulated rebalance values. **`songStyles.md` (repo root) is the reference for every genre** (rule, price, tunables, file locations, simulated win %): any change to genre logic, rule text, prices or genre tunable defaults, or adding or removing a genre, must update it in the same change (the style files carry a KEEP IN SYNC note); when win rates or previous prices change, `src/songbook/data.ts` (the `/songbook` page) needs the same update.
- **Style lab**: data-defined styles (`src/game-logic/styles/specs.ts`) — roll modifiers with conditions (die type, element, first play, combos, target level, fame rank, showdown), multiplier changes, event rewards (tame, miss — optionally keeping the song, clear, take a bow, turn start, showdown end), economy changes (`src/engine/economy.ts`) and Inspiration rules. The engine applies any a player holds in `Player.specStyles` (none in normal play); built-in styles roll through the same generic `rollWithOptions`, which `src/sim/odds.ts` mirrors exactly so the smart bot plays specs correctly. The catalog of 100 experimental styles is `src/data/styleSpecBatches.ts`; `npx tsx scripts/style-lab.ts` (`BATCH=n`, `SPECS=a,b`, `PARALLEL=k/n`) simulates them, and results live in `docs/style-lab-report.md`. `OPP=1 ROUND=5 scripts/style-audit.ts` is the realistic way to judge a style's power and price: it goes on the tested bard's shelf from round 5 (the median round in which bots buy their first style, measured by `scripts/style-timing.ts`), they buy it at its real price ahead of dice upgrades, and the other bards shop for styles too, so a balanced style wins about a third of games (parity). Holding a style from round 1, or testing against rivals with no styles, overstates every style and should not be used to set prices.
- **Dice upgrade path**: d4 → d8 → d12 → d20 (2/2/4 EXP; a new d4 costs 1 — totals 1/3/5/9, so every upgrade step pays roughly the same damage per EXP). Every bard starts with one d8 of their chosen element, in song 1.
- **EXP scale**: EXP is a small, tight currency — monsters pay 1 per level and everything in the Studio costs single digits. All of it is tunable (`monsterExpPerLevel`, `newD4Cost`, `upgradeCost*`, `inspirationBaseCost`/`Step`).
- **Opening board**: monster chips are dealt from an exactly balanced pool — the same count per element — shuffled across the spaces (`dealBalancedGenreTags`), so no element is over- or under-represented at setup. `ensureStarterChips` then swaps chips so every bard's starting space holds a monster of their own element, keeping the per-element totals intact.

## Playtest debug mode

`DebugPanel/` is a live tuning console for playtesting. Open it with `?debug=1`, the Menu's "Playtest Console" entry, or Ctrl/⌘+Shift+D.

- **Values** — every tunable, grouped, with sliders and clamped number inputs
- **Players** — per-player fame/EXP/Inspiration/position/counters, plus phase, round, turn index and shortcuts ("arm showdown", "jump to fame gate")
- **Simulate** — pick a pace (Learning / Typical / Expert, `src/data/simulationPaces.ts`) and a round with a large −/+ stepper, then **Play on from round N+1** or **Showdown after round N** (`DEBUG_SIMULATE`: bots replay this table — same bards, elements and tunables — from a fresh deal through the real engine). The expert bot is far ahead of people (6 dice in ~4 elements by round 5), so the tab defaults to Typical; slower paces set `SmartParams.skill` below 1, making the bot slip like a person (random move/play/purchase, skipped Studio visits, fewer encores). An action without `pace` plays at expert
- **Board** — add/remove monster chips per space, clear the board, respawn monsters
- **Presets** — save the whole `EngineState` to the server under a name, then reload it later or share `?preset=<id>`

The simulation plays with the **smart bot** (`src/sim/smartBot.ts`), driven by exact roll/damage distributions (`src/sim/odds.ts`, verified against the engine's dice in `odds.test.ts`): it picks each fight play by tame probability and the cost of losing the song (a tame returns the die), prices rerolls/Inspiration by stage and banks Inspiration for the showdown, uses Blues / Bebop / Gospel calls / Soul / featured songs deliberately, wounds untouched monsters for EXP, shops by how much each option raises its odds against the monsters on the board (genres and genre pairs included), and plans showdown verses around the boss's immunity. `simulateRounds` runs it inside the reducer (`simulateToRound`), so it works the same in hotseat and on the server. The original greedy bot in `src/sim/bot.ts` stays as the yardstick: `npx tsx scripts/bot-tournament.ts [games] [lineup]` plays mixed tables (e.g. `SBB`; `PARAMS`/`VS` env vars tune or pit variants, `TUNE` overrides tunables for every seat) — the smart bot wins ~86% head-to-head and ~76% of seats against two baselines. `scripts/style-audit.ts` measures styles and style pairs (`STYLES=a+b`, `PAIRS=1`) with smart bots in every seat. If a bot game reaches the showdown before round N, up to 12 games are tried and the furthest is used (rounds are capped at `MAX_SIMULATED_ROUND`). `src/data/roundProfiles.ts` holds, per pace, when bot games typically reach the showdown and what a bard holds after each round (both shown next to the control); it is GENERATED by `npx tsx scripts/sim-round-profiles.ts` (~2.5 min), which also prints per-round holdings — regenerate after balance changes or retuning the paces.

Edits flow through host-gated engine actions so online games stay server-authoritative: `DEBUG_PATCH` (partial tweaks, every value clamped), `DEBUG_LOAD_STATE` (full state replace, used by preset restore) and `DEBUG_SIMULATE`. Presets live in Redis behind `api/debug/presets` (90-day TTL, newest-first index capped at `MAX_PRESETS`). Set `LUTE_HERO_DISABLE_DEBUG=1` to turn the preset endpoints off on a deployment.

## Deploying online multiplayer (Vercel)

1. Import the repo into Vercel (framework: Vite). `api/**` deploys as Node functions automatically; `vercel.json` raises `maxDuration` for the SSE stream.
2. Add **Upstash Redis** from the Vercel Marketplace (or set `UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN`, or the `KV_REST_API_*` equivalents). Without them the API falls back to per-invocation in-memory storage, which does NOT work across serverless invocations — Redis is required in production.
3. Hobby-plan note: streams rotate every ~300s (the client reconnects seamlessly); each connected client polls Redis ~2x/s.
